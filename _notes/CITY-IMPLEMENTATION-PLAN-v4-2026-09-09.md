## T-pr20 — Two tent rows staked at Quickstart (S)

**depends_on:** none. **Rationale:** "housing = two tent rows"; founding stays unpriced.

**Mechanics.** PR #20 stakes ONE `tent` lot at (21,9)-(26,12) receiptlessly in `RunCore` after `VerifyFounded` (`feat/tent-playtest-2:World/KingdomQuickstartBootstrap.cs:141`; `…Bootstrap.Shelter.cs:22-64`). Re-key and double it:

- Two lots: A (21,9)-(26,12) unchanged; B (21,13)-(26,16), directly south; `ShelterX2 < 31` still holds (the heart survey begins at x=31), clear of role cells at x=28 and start (40,12) (`Core/KingdomQuickstartRules.cs:20-29`). Replace the four `ShelterX1..Y2` constants with a two-element `ShelterLots` array of `PlotRect`s; `RequiresPreparedGround` (`feat/tent-playtest-2:Core/KingdomQuickstartRules.cs:75-86`) ORs both.
- `TryStakeShelter` loops the two lots; find-before-stake per lot via `ShelterMarkerProperty` (value = plot id, `Shelter.cs:102-124`), so a cut after lot A stakes only B on resume.

2. **Physical rollback does not undo the model.** `KingdomCreed.Record` writes the creed property **and** increments `System.CreedCounts` (`Core/KingdomCreed.01.ResidentHistory.cs:30-33`); `KingdomResidents.TryEnsureRow` publishes a resident row into the seated city book (`Simulation/City/KingdomResidents.03.RosterAndEnrollment.cs:205-213`, the publish at `:209`) and binds it at `:214`; `KingdomFounding.EnrollCitizen` writes citizenship. `RemoveFreshGrantObject` obliterates an object (`World/KingdomQuickstartBootstrap.Allocations.cs:48-65`) and knows nothing about any of that. Undoing them means the journalled departure authority (`Simulation/City/KingdomResidents.04.ResidentTransitionsAndAccession.cs:48-71`, which demands a `KingdomResidentDestructionAuthorization` and a `KingdomResidentDepartureOperation`) — far too heavy to run inside a boot callback, and it still cannot un-increment a creed tally.
3. **A stalled receipt stops retrying.** `TryResume` compares the raw wire against `AttemptedReceipt` and returns if they match (`World/KingdomQuickstartLifecycle.cs:55-56`), setting it at `:60`. `AttemptedReceipt` is cleared on `AfterGameLoaded` and `ZoneActivated` (`:32,39`) but **not** on `EndTurn` (`:44-48`). So a wake that changes nothing gets exactly one attempt per load or zone activation, and the `EndTurn` fallback path v2 relies on never fires again in that session.

The fix is to split the sequence at the reversibility boundary and to make progress always publish.

**Stage A — reversible, all-or-nothing, ONE scope.** Physical only: create the four bodies and register every piece of their `BaseFarmer` gear, place all four, verify all four. Nothing touches the creed, the roster or citizenship.
- One `TryCreateFreshGrant(` call for the whole cohort (`World/KingdomQuickstartBootstrap.Allocations.cs:10-25`). Its `PrepareAndPlace` closure creates body 1, then `scope.Create(() => item)` for each of body 1's inventory and equipped objects, then body 2 and its gear, and so on; it captures the four bodies into a local array and returns **body 1** as the ceremonial candidate, which is what `scope.Owns` and `Verify` are handed (`GrantScope.cs:22,47`). The `Verify` callback verifies **all four** from the captured array, not just the candidate.
- Why one call and not four: `TryExecute`'s rollback walks `Allocations` in **reverse** (`:63-67`), and because each body is allocated before its own gear, reverse order removes a body's gear before the body — which `RemoveFreshGrantObject` requires, since it refuses an object with unproved contents (`Allocations.cs:53`, `HasUnprovedGrantContents` at `:67-74`). Any failure anywhere in the cohort therefore unwinds all four bodies and all their gear, sets the quarantine fence first (`GrantScope.cs:58-61`) and releases it only if every removal succeeded (`:70`). That is exact zero-or-four for the physical half, using the shipped primitive verbatim.
- Placement cells (32,11) (34,11) (32,13) (34,13) — inside the approach band X29-37/Y11-13, off the heart rect and the role cells (`Core/KingdomQuickstartRules.cs:55-64`), each passing `EmptyRoleCell` (`World/KingdomQuickstartBootstrap.Recovery.cs:74-129`).
- On failure the receipt is republished **unchanged in phase but with `Pending` restated and the four ids cleared** — a no-op for a receipt that was already `Pending`, and therefore the one case where a wake makes no progress. That is acceptable precisely because Stage A leaves the world byte-identical to before it ran: the next load or zone activation retries from a clean slate, and the failure is logged through `MetricsManager.LogError` as `Lifecycle:61-63` already does.

**The publish between the stages.** With four verified bodies in hand and before a single irreversible write, publish `FoundersDisposition = Seeding` with the four object ids. Phase stays `Complete`. This publish is the durable fence: it changes the wire, so `AttemptedReceipt` no longer matches and the next `EndTurn` will wake again (defect 3 above); and it names the exact four objects, so a wake can find them without discovering ownership by walking the zone.

**Stage B — irreversible, forward-only, idempotent per founder.** For each of the four ids, in index order: resolve the object by id in the zone; then apply, and only if not already applied, `GiveProperName` + `KingdomName` + `KingdomOrigin` (= profile key), `KingdomFounding.EnrollCitizen(body, Founding, tick)`, `KingdomBorn = 1`, `KingdomCreed.Record`, and `KingdomResidents.TryEnsureRow` **after** placement (it binds on `Body.CurrentZone`, `KingdomResidents.03.RosterAndEnrollment.cs:179-181,214`). Each step has an exact, cheap "already done" witness — a non-empty proper name, `KingdomCitizen == 1`, `KingdomBorn == 1`, a non-empty `CreedProperty`, a located resident row — so re-running Stage B after a crash repeats nothing.
- **`KingdomCreed.Record` is the one non-idempotent step** and needs the guard spelled out: it increments `System.CreedCounts` unconditionally (`Core/KingdomCreed.01.ResidentHistory.cs:31-32`), so it is called only when `Settler.GetStringProperty(CreedProperty)` is empty. Pin that guard by source; a second call would inflate the tally by up to four and no later code would notice.
- When all four are complete, advance in one publish: `Phase = FoundersSeeded`, `FoundersDisposition = Seeded`, four ids retained. `ProjectCompatibility` then reads Population 4 with no seeder bookkeeping (`Simulation/City/KingdomResidents.00.IdentityAndRoll.cs:176-182`).
- If a wake in `Seeding` finds an id that no longer resolves, or resolves to a foreign or malformed object (the `ForeignOrMalformed` observation, `Core/KingdomQuickstartRules.cs:185`), it can neither complete nor reverse: publish `Faulted`, announce once, never retry. `Faulted` is terminal and honest — the world has 1-3 founders and says so — and it is unreachable except through a crash inside Stage B, which is itself a few hundred ticks of pure model writes with no I/O.

**Phase advance is a phase advance; disposition change is not.** `TryAdvance` refuses anything that is not exactly one phase forward (`Core/KingdomQuickstartRules.cs:122`), so the within-`Complete` moves (`Pending → Seeding`, `Seeding → Faulted`, `Stage A failure → Pending`) get their own pure function `TryRestateFounders(Current, Disposition, Ids, out Advanced)` beside it, with the same `Valid(copy)` gate at the end (`:167`). `TryAdvance` itself gains the founders disposition only for the new `FoundersSeeded` case and refuses any other value elsewhere, mirroring exactly how it threads `AdvisorDisposition` today (`:128,133,138,143,162`).

## T-forage-1 — Brush-forage duty with exhaustion (M)

**depends_on:** T-storage-1, T-camp. **Rationale:** citizens forage brush by destroying nearby vegetation; when exhausted, other methods. **Always-on under the ceiling (ruling 9)** — no Charter switch, no option.

**Mechanics.** A standing duty in `KingdomMaterials.OnSettlementPass` (`Growth/KingdomMaterials.10.SettlementPassAndYards.cs:32-97`), fourth in the "one gang, one job" queue: yards, strike, staked clearance, then forage — an explicit order outranks a chore. Modelled on `WorkClearance` (`Growth/KingdomMaterials.14.ClearanceWork.cs:30-190`), including its vetoed/announce shape at `:96-128` and its `KingdomOrdinaryCustody.TryProveEmpty` check before `Obliterate` (`:107-108`).
- **State:** `[Serializable] r_KingdomForage : IPart` in `XRL.World.Parts` on the heart plot root: `long LastWorkedTick; bool NoHandsAnnounced, NoBrushAnnounced, NoRoomAnnounced, EnoughAnnounced;` no `WantTurnTick` (`Growth/KingdomMaterials.00.r_KingdomClearance.cs:17-63` shape). New part on a new object property set — no shipped part gains a field.
- **Constants (ruling 8), all named and tunable in `Growth/KingdomMaterialRules.Forage.cs`:** `BrushPerForagerPerDay = 1`, `MaxForagingHands = 3` (vs `MaxClearingHands = 6`, `Growth/KingdomMaterialRules.Clearance.cs:24-33`), **`ForageRadius = 12`** (flat Chebyshev from the rite cell, clamped to the zone — v1's `12 + 4·(rung−1)` widening is **deferred** until brush density is measured natively), **`ForageCeilingUnits = 12`**. Hands = `min(MaxForagingHands, FreeHands(Population, AssignedCrew))` (`KingdomMaterialRules.Clearance.cs:130-134`). One tent row's canvas:3 = three settler-days.
- **Saturation (M10 — the correctness fix).** `ElapsedDays` is uncapped (`Core/KingdomRules.Economy.cs:125-136`), so after a 100-day absence a naive `hands × days` would obliterate 300 plants in one activation. The rate is `min(hands × ElapsedDays × BrushPerForagerPerDay, ForageCeilingUnits − heldBrush)`, and the second term is **the hard bound applied every pass regardless of `ElapsedDays`**. With the ceiling at 12 and a full store, a 100-day absence forages nothing.
- **Checkpoint advancement, and why it cannot wait on the forage's own turn (B9 — the second correctness fix).** `OnSettlementPass` is a one-gang-one-job queue with a hard early return: `if (strike != null) { WorkStrike(…); return; }` at `Growth/KingdomMaterials.10.SettlementPassAndYards.cs:88-92`, and the clearance job below it at `:93-96` spends the same `hands` the forage would want (the method's own doc comment at `:25-27` says a second job waits for the next pass rather than being worked by hands the first one already spent). Forage sits fourth, so on any pass where a strike order stands the forage body never runs at all. If `LastWorkedTick` were advanced only *inside* that body, those days would be **banked**: `KingdomRules.ElapsedDays(now − LastWorkedTick)` (`Core/KingdomRules.Economy.cs:125-136`) would then return every day the gang spent striking, and the first pass after the strike finished would pay a week of foraging for a week in which nobody foraged. The rule is therefore:
  - `r_KingdomForage.LastWorkedTick` is advanced on **every** settlement pass that reaches `OnSettlementPass` for this zone, whether or not forage does any work. The advance is placed **above** the `strike` early return at `:88`, beside the yards loop, so no queue outcome can skip it.
  - The advance uses the shipped whole-day-carry checkpoint mover (`Core/KingdomRules.Economy.cs:138-142`), which moves a "last resolved" stamp forward by exactly the whole days a caller just charged and keeps the part-day remainder for the next one — so the stamp never runs ahead of what was actually spent.
  - Zero on a fresh part still means "never worked": the first pass stamps `now` and forages nothing, exactly as `r_KingdomClearance.LastWorkedTick` is documented to behave (`Growth/KingdomMaterials.00.r_KingdomClearance.cs:48-49`).
  - This is belt-and-braces with M10, not a substitute for it. M10 bounds a single pass's yield at `ceiling − held`; B9 stops the days themselves from accumulating, which matters on a save whose ceiling has room. Both are pinned separately.
- **Ceiling.** Forage only while `Stock(Z).Get(Brush) < ForageCeilingUnits`; above it, say once "The stockpiles hold brush enough; the scrub is left standing." (STANDARDS §7 — no scenery stripped for nothing.)
- **Candidate predicate (R5 + M9 — rewritten).** `TryClassify == KingdomStanding.Brush` is **not** a plant test: it also returns `Brush` for any wall with `BodyType` ClothWall / PlantWall / FungusWall, or a `PaintedWall` of `wall_plant` / `wall_mushroom` (`Growth/KingdomMaterials.15.GroundAndWalls.cs:150-154`), and vanilla `CanvasWall` **is** `BodyType ClothWall` (`B/ObjectBlueprints/Walls.xml:831`) — so under v1 the camp's own canvas ring and a neighbour's tents and fungal cave walls were candidates. The predicate is therefore an explicit tag test:
- has tag `Plant` **or** `LivePlant`, **and** `!object.IsWall` (or equivalently no `Wall`/`PaintedWall` part);
- `!IsCreature` — `ActivePlant` descendants (Yonderbrush, Lurking Beth, Lagroot…) carry tag `Creature` + `Brain` (`B/ObjectBlueprints/Creatures.xml:1032-1049`) and are already excluded by `TryClassify:88-90`; state it so nobody re-adds them;
- **not `Harvestable`** — Watervine, Yuckwheat, Urberry Bush, Lahbloom and Noisegrass are the player's food AND the mod's crop sources (`Growth/KingdomCropRules.CropMapping.cs`, `Growth/KingdomCrops.04.Rows.cs`); without this the camp cuts its own larder;
- not a crop row cell, not inside any plot rect, not inside the heart rect — **and this exclusion is pinned**, because neither `TryClassify` nor `IsProtected` excludes `PlotPartProperty` objects (`GroundAndWalls.cs:26-68,105-115`);
- `!IsProtected`; no `Physics.Owner` (the wild-seed rule, `Growth/KingdomCrops.03.WithdrawalAndWildSeed.cs:88-94`); no untaken `r_KingdomWildSeed`; not tagged `Tree`. Nearest-first, ties by (y,x) — deterministic on reload.
- **Per plant:** `TryProveEmpty`, then the measured `Obliterate(Silent:true)` ladder (`ClearanceWork.cs:114-128` — credit only when `gone || !GameObject.Validate(item)`, veto and name the plant otherwise), `KingdomSurvey.ObserveRemovedFromActive`, then `MaterialStock.Put(Brush, 1, plantCell)` (`ClearanceWork.cs:117-123,134`); a full stockpile spills the bundle on the plant's cell (T-storage-1's refuse-and-spill). `Obliterate` goes through `BeforeDestroyObjectEvent` (`D/XRL/World/GameObject.cs:4050-4062`) and no vanilla base-`Plant` descendant carries a spawn- or gas-on-destroy part, so the only world side effect is permanence: vanilla zones do not regrow.
- **Announcements (§7b):** no hands — "The camp has nobody free to cut scrub."; no room — "The stockpiles will not take another bundle; it is stacked where it was cut."; exhausted (zero candidates) — "The scrub within {r} paces of {seat} is cut out. There is nothing left here to bind canvas from." Flags clear when the block lifts. Exhaustion is the hand-off to T-forage-2.

**Files (production).** New `Growth/KingdomMaterials.00.r_KingdomForage.cs`, `Growth/KingdomMaterials.16.ForageWork.cs`, `Growth/KingdomMaterialRules.Forage.cs`; `Growth/KingdomMaterials.10.SettlementPassAndYards.cs` (the checkpoint advance above `:88`, and the queue tail at `:88-96`); `Core/KingdomReports.cs:81-160` (status line); `Core/KingdomRemovalCoverage.Generated.cs` (regen for the part).

## T-storage-3 — Store filters + auto-sort duty + Charter filter UI (L)

**depends_on:** T-storage-1, T-storage-2. **Rationale:** "category + weight + value rules so a dump chest gets emptied to the right stores over time (or instantly)". **First slice is category filters only (ruling 14)** — weight and value bands are deferred.

**Prior art (memory, unverified):** DF/RimWorld/ONI/Factorio/Minecraft sorters all reduce to a typed FILTER on the destination, a deterministic PRIORITY, and a visible FULL state; RimWorld's per-pawn per-tick hauler is the pathology `Simulation/City/KingdomLogisticsRules.cs:3-27` refuses. Engine: no container sorting exists (`D/XRL/World/Parts/Rummager.cs:43-57` is creature-side, own cell).

**Filter.** One string property `KingdomStoreFilter` on the container; absent = `any`. Vocabulary: `intake` (source only), `materials` (the nine `KingdomMaterial`s), `finds` (exotics), `bits`, `any`. **No `:heavy` / `:light` / `valuables` bands in this slice (ruling 14)** — `Physics.Weight` and `Commerce.Value` stay unread by the mod, and the vocabulary parser is written so a band suffix is a recognised-but-rejected value with a named error rather than a silent `any`. Routing keys off `TryOrdinaryMaterialOf` / `TryExoticOf` / `TryBitsOf`, never `GetInventoryCategory()` (which returns "???" while Confused, `D/XRL/World/Parts/Physics.cs:3073-3085`). The filter NEVER gates counting — a mis-set filter must not erase timber from the ledger. Storehouse blueprints declare `materials` (T-storage-2).

**The ordering key (R4 — the blocking fix).** `KingdomDedicationOrder` is stamped **only** on water vessels and larders: `StampDedicationOrder` walks `Survey.Stores[i].ParentObject` and `Survey.Larders[i]` (`Simulation/City/KingdomCity.z11.DedicationAndHelpers.cs:29-38`), called from the reckon path (`z04.ReckonAndSpend.cs:33`). Material stockpiles never receive it, so `DrainOrdinal(0) == int.MaxValue` for every one of them (`z11:71-80`) and "lowest ordinal" would be a total tie with no frozen key. **The key is a creation ordinal stamped at dedication:** extend `StampDedicationOrder` with a third loop over `Survey.MaterialStockpiles` (`Growth/KingdomSurvey.00.Declarations.cs:181`) through the same private `Stamp` helper and the same `System.DedicationCounter`, so a stockpile is numbered the first reckon after it is dedicated and keeps that number for life. The alternative (PlotId + cell) is rejected: it is recomputed rather than stored, and it changes when a plot is re-sited. An unstamped container still sorts LAST, which is the documented law at `z11:71-76` and now covers a stockpile dedicated between reckons.

**Sort step host — one pass, not two (B8, the first correction).** v3 hung the sort on `OnSettlementPass` **and** a second daily hook in `Core/KingdomSystem.z20.Events.cs` / `Simulation/City/KingdomHeartbeat*`, keyed on `AdvanceCheckpoint`. That second hook is unnecessary and unsafe, because ruling 13 is already satisfied by the first. `KingdomHeartbeat.OnEndTurn` **already runs the attended semantic pass** — `KingdomSystem.Guard("semantic", … KingdomSemanticDispatcher.OnEndTurn(System, seated, now, AttendedPass))` at `Simulation/City/KingdomHeartbeat.cs:167-173` — and `KingdomSemanticDispatcher` is the shared durable checkpoint: both entries, `OnZoneActivated` (the activation pass) and `OnEndTurn` (the stationary daily pump), funnel through one `TryDispatch` with one `[ThreadStatic]` reentrancy flag, one `KingdomSemanticClockRules.Decide`, and publish the same `System.LastSemanticTick` only when the pass returns true (`Simulation/City/KingdomSemanticDispatcher.cs:34-77`). That one canonical pass is `KingdomSystem.AttendSeatedSemantics` (`Core/KingdomSystem.z21.SemanticPass.cs:12`), reached from `Core/KingdomSystem.z20.Events.cs:59-66` behind `KingdomMaster.ObserveAutomaticWake` (`:55-56`) and `ExternalOwnershipAllows(ActiveZone)` (`:57-58`) — and it is that pass which calls `KingdomMaterials.OnSettlementPass` at `Growth/KingdomGrowth.z01.Activation.cs:219`.

So: **the sort duty is one job inside `KingdomMaterials.OnSettlementPass` and nothing else.** It then runs on zone activation AND once per city-day while the founder stands there — ruling 13, by construction — under one checkpoint, one reentrancy guard, one master-pause gate and one external-ownership gate, with no way for two hooks to fire in the same day and no way for a step to land outside the checkpoint. The **budget** falls out of the same fact: the canonical pass is once per city-day, so the per-pass step budget *is* the daily budget (one step by default; `MaxOpenJobs = 16` under the instant option). M7's point survives unchanged in substance — the host's gates are inherited and wanted; they are simply already inherited, and no new hook is needed to inherit them. `Core/KingdomSystem.z20.Events.cs` and `Simulation/City/KingdomHeartbeat*` therefore leave this ticket's file list: a deliberate non-change to state in the PR body, like the envelope in T-storage-2.

**Sort step** — one job in the queue, after forage.
1. Source = `intake` container with the lowest `KingdomDedicationOrder` (`KingdomCityRules.DrainOrdinal`, `z11:71-80`) holding a classified item; not `FetchMarkProperty`-marked.
2. Item = first classified item in list order passing `KingdomConstructionInputLeaseAuthority.TryObjectGraphAvailableForOrdinaryTransfer` (the Fetch predicate pair, `Quests/KingdomBounty.WorkAndCarry.cs:124-137`).
3. **Destination, with the fallback corrected (B10).** First choice: a non-intake stockpile whose declared filter **accepts the item's class** and whose room is at least the units about to be bound, lowest ordinal winning. Fallback: a stockpile whose filter is **`any`** — absent counts as `any` — with room, lowest ordinal. v3's fallback said "any non-intake with room", which is wrong: `finds` and `bits` are non-intake filters, so a materials bundle would land in a finds-only store and the founder's own declared law would be broken by the mod's own duty. Nothing else is a legal fallback: an `intake` store is the source class, and a `materials`/`finds`/`bits` store that refused the class in the first choice refuses it here for the same reason. If neither choice yields a destination: announce once (`KingdomSortBlockedAnnounced`) and stop.
4. **Units, split before binding (B4, the first blocking fix).** v3 said "move ≤ `CarrierCapacity = 12` units — split by `Count`", and T-storage-1 gave the Fetch carry a `room >= 1` check. Both are wrong against the shipped binding. `Quests/KingdomBounty.WorkAndCarry.cs:146` binds `Data.TransferUnits = next.Count` — the **whole stack**, whatever its size — and `ContinueTransfer` then refuses to proceed unless `item.Count == Data.TransferUnits` (`Quests/KingdomBounty.Transfer.cs:146`). There is no partial move inside the ladder: the object that leaves the source is the object that arrives. Therefore:
   - **`room >= 1` is not an admission test.** The destination must have `room >= boundUnits`, or a 30-unit stack lands in a store with one unit of room and the cap is a fiction. T-storage-1's `Put` room check is unaffected — that is a *fill-to-room* loop over a created stack (`Growth/KingdomMaterials.04.MaterialStock.cs:148-156`) — but its line "the Fetch bounty carry gets the same room check" is restated there and here as **`room >= next.Count`**.
   - **Splitting happens before the phase leaves `None`.** Clamping to `CarrierCapacity = 12` (`Simulation/City/KingdomLogisticsRules.cs:41`) or to the destination's room means creating a second stack object, and every witness in the ladder is captured against a frozen `InventoryFrame` (`Transfer.cs:27-61`) — a split mid-ladder mutates the source list under its own proof and quarantines. The split is performed while `TransferPhase == None`, inside the source inventory, by the ordinary engine stack split; both resulting objects are then ordinary source contents, and only **then** is one of them bound with its own exact `Count`.
   - **Room is re-read per transfer.** The chooser runs again for every bound stack, because the previous transfer consumed room in the store it chose. Picking one destination and then pushing n stacks into it is the same defect one level up.
5. **Move with the shared primitive:** lift `InventoryFrame`, the witness predicates and the `BountyTransferPhase` ladder (`Quests/KingdomBounty.Transfer.cs:14-25,63-140,144-242`) into `Growth/KingdomStoreTransfer.cs`; the Fetch bounty and the sort duty both call it (two movers that can drift is the failure `KingdomLogisticsRules.cs:19-23` names).

**The transfer primitive, and the proof it cannot be lifted as-is (B1, the second blocking fix).** `InventoryMinusExact` (`Transfer.cs:88-113`) proves two different things at once: **(a)** the *source list* lost exactly one entry and every survivor is unchanged (`:93` `Frame.List.Contains(Removed)`, `:101` the count, `:102-111` the survivors), and **(b)** the removed object is in *detached custody* — `Removed.Count == Units && Removed.InInventory == null && Removed.CurrentCell == null` (`:92-93`). `InventoryPlusExact` (`:115-130`) proves the destination gained it and, at `:119`, that `Added.InInventory == Frame.Owner`. The post-remove assertion at `:192-193` wants (a) + (b) and gets them. The **post-add** assertion at `:225-226` calls `InventoryMinusExact(sourceFrame, item, units)` **and** `InventoryPlusExact(destinationFrame, item, units)` in the same breath — that is, it demands `item.InInventory == null` and `item.InInventory == destination` at the same instant. The pair is unsatisfiable: a successful `AddObject` at `:213` makes (b) false, a failed one makes `InventoryPlusExact` false, and either way the ladder quarantines at `:230`. Lifting the file verbatim would hand the sort duty a mover that can never complete a single transfer.

The extraction must therefore **split the two proofs before it moves the code**:
- `SourceListMinusExact(InventoryFrame Frame, GameObject Removed)` — clause (a) only: `InventoryHeaderExact`, `!Frame.List.Contains(Removed)`, exactly one matching index in `Frame.Items`, `Frame.List.Count == Frame.Items.Length - 1`, every survivor exact by reference / id / count / owner / cell.
- `DetachedCustodyExact(GameObject Removed, int Units)` — clause (b) only: validated, `Count == Units`, `InInventory == null`, `CurrentCell == null`.
- Post-remove (today `:192-193`) calls **both**, plus `InventoryOriginalExact(destinationFrame)`. Behaviour unchanged, byte for byte in effect.
- Post-add (today `:225-226`) calls `SourceListMinusExact(sourceFrame, item)` and `InventoryPlusExact(destinationFrame, item, units)`. Detached custody is deliberately **not** re-asserted there, because at that instant the item is by definition no longer detached.
- Every quarantine string, phase name and receipt field is preserved verbatim. This is a decomposition of one predicate, not a loosening of the ladder, and each clause keeps its own pin.

This changes the shipped Fetch carry as well as the new sort duty — the same primitive serves both, which is the whole point of lifting it — and it is why the ticket's **headline test is a successful transfer, end to end, in both callers**. On `origin/dev` = f2a5d83 no such pin exists; whether the defect is observable in play today is **INFERRED** (a Fetch bounty reaching `ContinueTransfer` should quarantine on its first successful add, and nothing in the tree proves it does not).

**Interrupted sorts quarantine, deliberately — the resume idea is withdrawn (B5, the third blocking fix).** v3's native check said "save/reload mid-`AddIntent` resumes without duplication". It cannot. `ContinueTransfer` opens with `if ((BountyTransferPhase)Data.TransferPhase != BountyTransferPhase.Bound) { Quarantine(…); Data.TransferPhase = Quarantined; return false; }` (`Quests/KingdomBounty.Transfer.cs:132-139`) — **every** re-entry in any phase but `Bound` is quarantined, with the shipped message "A fetch transfer reloaded after a mutation intent; neither callback was repeated." `RemoveIntent`, `Detached`, `AddIntent` and `Arrived` are all set inside one synchronous call (`:178,201,202,234`), so the only way to observe one of them at re-entry is a save or a crash between the two engine callbacks. The design refuses to repeat a callback it cannot prove, and that refusal is correct. So this ticket **retains the quarantine** and says so plainly:
